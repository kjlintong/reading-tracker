## 二、导入适配中的三个真实坑

### 坑 1：星级是 emoji ⭐️，不是 ★

Notion 用的是 `U+2B50` + 变体选择符，常规 `★`（`U+2605`）匹配不到，会全部解析成 0 分。
现在两种都支持。

### 坑 2：日期 off-by-one

```js
new Date("April 18, 2025").toISOString().slice(0,10)  // ❌ "2025-04-17"
```

`new Date()` 按本地时区解析，`toISOString()` 转 UTC 后回退一天。
必须改用 `getFullYear()/getMonth()/getDate()` 本地字段拼装。

### 坑 3：想读书目的单日期是「加入书架日」，不是「开始阅读日」

79 本中有 15 本 Want to Read 的 `Dates` 都是同一个 `2024-06-27`（批量导入时间）。
若一律写进 `startedAt`，统计"开始阅读"会失真。
现在按语义分流：日期范围或已读 → `startedAt`；其余单日期 → `extra.notionAddedAt`。

### 导入结果

```

状态：想读 38 · 已读 38 · 在读 3
有完成日期 36 本 · 有评分 35 本 · 有起止日期 35 本
金句 12 条，11 条可关联到书
```

## 三、微信读书官方 Skill（v1.0.4）——重要修正

网关响应里提示有新版本，从 `https://cdn.weread.qq.com/skills/weread-skills.zip`
拿到了官方文档，**纠正了三个凭字段名猜测一定会错的地方**：

| 项 | 错误认知 | 官方实际 |
|---|---|---|
| skill_version | 1.0.3 | **必须是 1.0.4**，否则回包持续带 upgrade_info |
| 阅读进度 | 在 `/shelf/sync` 里 | **不在书架接口**，需单独调 `/book/getprogress` |
| 时长单位 | 分钟 | **全部是秒**（totalReadTime、recordReadingTime） |
| progress 语义 | — | 0-100 整数，**1 表示 1% 不是 100%**，只有 100 才算读完 |

### 可用接口清单

| 接口 | 用途 |
|---|---|
| `/shelf/sync` | 书架（books 电子书 + albums 有声书 + archive 书单 + mp 文章收藏） |
| `/book/info` | 详情：简介、分类、出版社、ISBN、译者、字数、评分 |
| `/book/getprogress` | 阅读进度 + 累计时长（秒）+ 读完时间 |
| `/book/chapterinfo` | 章节目录 |
| `/store/search` | 书城搜索（元数据补全主力） |
| `/readdata/detail` | 阅读统计（weekly/monthly/annually/overall） |
| `/user/notebooks` · `/book/bookmarklist` | 笔记与划线 |

**书架条目总数口径**：`books.length + albums.length + (mp 非空 ? 1 : 0)`。

### 补测：书架条目到底给了哪些字段（2026-09-29 二次抓包）

原始响应存于 `tools/samples/weread-shelf-raw-live.json`（55 本）。
**每本书只有 10 个字段**，不多不少：

```
bookId  deepLink  title  author  updateTime  cover
finishReading  readUpdateTime  secret  category
```

由此确认两个关键结论：

1. **没有 `readingProgress`，也没有 `markedStatus`。** 书架接口给不出百分比，
   想拿进度只能逐本调 `/book/getprogress`。55 本 = 55 次请求，
   所以 App 里把「同步阅读进度」做成独立动作，而不是每次书架同步顺带跑。

2. **`readUpdateTime` 恒大于 0**，哪怕从没读过的书也有值——
   实测《黑马波段操盘术》`readUpdateTime=1616718207` 反而**早于**
   `updateTime=1760179191`（那是入架之前的历史时间或平台默认值）。
   所以 `readUpdateTime > 0` 是个会误判的判据，**必须比时间先后**：

   | 情形 | 判据 | 实测条数 |
   |---|---|---|
   | 已读完 | `finishReading == 1` | 0（该快照里无） |
   | 在读 | `readUpdateTime >= updateTime` | 18 / 55 |
   | 想读 | `readUpdateTime < updateTime` | 37 / 55 |

   注意顺序：`finishReading` 优先，因为读完的书两个时间戳关系不一定还成立。

`/book/getprogress` 响应结构（实测）：

```json
{"bookId":"3300062053",
 "book":{"chapterUid":296,"chapterIdx":2,"updateTime":1790664442,
         "readingTime":64,"progress":0,"isStartReading":0,
         "recordReadingTime":0,"ttsTime":0,"startReadingTime":0}}
```

坑：`recordReadingTime` 与 `readingTime` 是两个不同字段，实测出现过
**`recordReadingTime=0` 而 `readingTime=64`**。用 `recordReadingTime ?? readingTime`
兜底会得到 0（因为 `0 ?? x` 就是 0），一本读了 64 秒的书会被记成 0 秒。
正确做法是取「第一个大于 0 的值」。

另：`progress=0` 但 `chapterUid` 已有值、`readingTime=64` 的情况存在——
说明用户打开过、翻了一点页，但还没越过微信读书计入百分比的门槛。
所以**不能拿 `progress` 判断有没有读过**。

## 九、大模型接入实测（商汤 Sensenova）

配置：`https://token.sensenova.cn/v1`，模型 `sensenova-6.8-flash-lite`。

### 性能实测

| 模式 | 耗时 | 说明 |
|---|---|---|
| 单本补全 | 25–51 秒 | 逐本调用，91 本需约 40 分钟 |
| 批量补全（5 本/批） | 约 30 秒/批 | **91 本仅耗时 152 秒** |

批量化把总耗时压缩约 **15 倍**，且质量无损。

### 踩坑一：JSON 解析失败

即便开启 `response_format: json_object`，模型仍可能返回
**无外层方括号的对象序列**：

```
{"index":0,...},{"index":1,...},{"index":2,...}
```

直接 `JSON.parse` 报 `Unexpected non-whitespace character after JSON`。
修复方式：逐层降级解析——先原样解析，失败则外加 `[]` 再解析，
最后用正则抓取最大括号片段。Node 侧（`parseJsonLoose`）
与 Dart 侧（`_parseJson`）均已同步修复。

### 踩坑二：报告生成超时

默认超时 60 秒不足以生成长报告，触发 `AbortError`。
报告场景单独放宽至 180 秒。

### 踩坑三：分类体系分裂（影响统计正确性）

微信读书返回自有分类体系，与受控词表并存，导致同一语义分裂成多个标签：

```
经济理财 18 本 + 经济 9 本   ← 实为同一类，却分列两处
哲学宗教 7 本 + 哲学 13 本
个人成长 13 本 + 心理 19 本
```

这会让统计图表出现重复类别。解决方案：建立 `CATEGORY_ALIASES` 映射表 +
`normalizeCategory()` 函数，在数据落库前统一归口。归一化后分类种数由 21 降至 14。

**设计权衡**：最初把「个人成长」并入「心理」，导致心理类占比虚高至 24%，
掩盖了真实阅读结构。改为单列「成长」分类后，分布更贴近实际。
